# 19 — ADR-CR101-MALL-SCOPE-ENFORCEMENT

**Status: ACCEPTED — PHASED IMPLEMENTATION (2026-08-21).** Architecture approved in principle by human decision. Phases 1–2 (descriptive metadata infrastructure, zero behavior change) authorized and completed — see `docs/changes/CR-101-PHASE-1-2-COMPLETION.md`. Phases 3–7 (actual enforcement) remain **NOT AUTHORIZED**, pending a separate human gate per phase. Per `docs/change-templates/ADR-TEMPLATE.md`, formalized here as the capstone decision record for CR-101.

## Current architecture

Mall-scoped authorization runs through a single global `MallAccessGuard` (`app.module.ts:114-117`, last in the guard chain after `ThrottlerGuard` → `JwtAuthGuard` → `RolesGuard`). It resolves a request's target Mall via a hardcoded set of query/body/param field names (`mallId`, `unitId`, `floorId`) and narrow path-substring heuristics (`contract`, `fitout`, `fitout-submittal`, `fitout-issue`, `/invoices/`), always keyed to `params.id` for the entity-lookup branches. `[ADMIN, CEO, TENANT]` bypass the guard entirely (`mall-access.service.ts:9`). When no Mall ID resolves from any source, the check is **silently skipped**, not denied (`mall-access.service.ts:262`).

## Problem

This produces a confirmed, exploitable class of defect (`CONTRA-008`, `docs/system-truth/ARCHITECTURE_CONTRADICTIONS.md`): any route whose identifying parameter isn't one of the guard's recognized names, or whose path doesn't match its substring patterns, is silently unscoped. Fresh verification this session found **17 confirmed-or-newly-found gap route groups** across 39 controllers (`15-CR-101-ROUTE-COVERAGE.md`), including two genuinely new findings (Announcements' staff-admin CRUD, Service-Catalog's proposal-linked routes) that a general audit hadn't previously surfaced — direct evidence that the heuristic's blind spots are not a fixed, enumerable list but a structural property that will keep producing new instances as the codebase grows.

## Options considered

1. **Patch each confirmed gap individually** (add an explicit `MallAccessService` call to each of the ~17 route groups). Rejected — explicitly out of scope per the review's mandate; does not address the root cause, so new routes will keep reproducing the same defect class.
2. **Flip the guard's fallback from skip-if-unresolved to deny-if-unresolved, immediately.** Rejected as a first step — would break every currently-unscoped-but-*intentionally*-global route (Health, Auth's public endpoints, Branding, base Categories, Telemetry, Users, Audit-Log) since the guard has no way to distinguish "forgot to scope this" from "this is deliberately global" without an explicit declaration existing first. Retained as the eventual Phase 6 outcome, but only after every route has explicit metadata (see Migration Strategy).
3. **Explicit, declarative, startup-enforced scope metadata per route** (this ADR's chosen design, detailed in `14-CR-101-SCOPE-MODEL.md`) — a single `@Scope(...)` decorator family, a centralized named resolver registry (`16-CR-101-RESOLVER-REGISTRY.md`), a startup-time completeness check, and a CI static gate. Chosen because it converts the failure mode from silent/runtime/discovered-by-incident to loud/build-time/impossible-to-ship, while remaining additive and low-risk through most of its rollout.

## Chosen architecture

Summarized from `14-CR-101-SCOPE-MODEL.md` and `16-CR-101-RESOLVER-REGISTRY.md`:

- Six formal scopes: `GLOBAL`, `COMPANY-SCOPED` (defined, unused today — no `Company` entity exists), `MALL-SCOPED`, `TENANT-SCOPED`, `USER-SCOPED`, `SYSTEM/INTERNAL`.
- One `@Scope(...)` decorator (class-level default, method-level override — mirrors the codebase's existing `@Roles()` convention), composable (AND semantics) when a route needs more than one scope simultaneously.
- Mall resolution via named, centrally-registered resolvers (reusing `MallAccessService`'s existing, already-correct per-entity lookup logic — this ADR does not propose rewriting working resolution logic, only how routes opt into it).
- Never trust a client-supplied `mallId` once an authoritative entity relationship exists (already correctly the case for a few resource types today; generalized to all).

## ADMIN/CEO bypass — resolved, not left as a blanket assumption

Investigated directly against real evidence (not merely inferred from role names), per the review's explicit instruction not to encode privilege policy from a role name alone:

- **`docs/audit/02-PERSONAS-JOBS-TO-BE-DONE.md:107-110`** (persona documentation, pre-dating this review) states explicitly: *"CEO gets cross-mall, analytics, approvals (final-tier), reports, ai — deliberately excludes day-to-day operational detail (no spaces/crm/bookings/tickets). ADMIN gets everything, including system config."*
- **ADMIN**: this documented intent — "gets everything, including system config" — is consistent with a genuine platform/technical super-admin persona. The current blanket Mall-scoping bypass for ADMIN is **CONFIRMED consistent with documented intent**, not merely assumed. Corroborated by `apps/frontend/src/components/MallContextModal.tsx:15-17`, where the frontend's own mental model already special-cases `isAdmin` as not needing to select a Mall context at all — independent confirmation the "ADMIN doesn't operate within a single Mall" assumption is baked in consistently, not just a backend shortcut.
- **CEO**: the documented intent is **narrower** than the current implementation. The persona doc scopes CEO's cross-mall capability to a specific set (dashboard, analytics, approvals-final-tier, reports, AI) and explicitly excludes day-to-day operational modules — yet `MODULE_ROLES` today includes CEO in `proposals` and `parking` as well (per `docs/ai-erp-team/03-DOMAIN-OWNERSHIP.md` history and this session's fresh `role-permissions.ts` reading), and the blanket `BYPASS_ROLES` mechanism gives CEO an unconditional Mall-scoping bypass for *every* module they have role-access to, not only the persona-documented five. **This is a confirmed, evidenced gap between documented intent and implementation** — not "no evidence found," but "evidence found, and it disagrees with the code." Also notable: `seed.ts:1576-1580` explicitly grants CEO `UserMallAccess` rows "to all malls," suggesting the original design may have intended CEO to go through normal Mall-access grants (like any other role) with the blanket bypass added later as a convenience shortcut that was never reconciled with the persona document.
- **Decision for this ADR**: `ADMIN` remains in `BYPASS_ROLES` unconditionally. `CEO` is proposed to be **removed from the blanket `BYPASS_ROLES` list** and instead receive Mall-scoping via its already-seeded `UserMallAccess` grants (i.e., CEO becomes a normal Mall-scoped role for modules outside its documented five, and only the five documented modules — Dashboard cross-mall, Analytics, Approvals final-tier, Reports, AI — get an explicit `CROSS_MALL_READ`-style permission, per Section "Cross-Mall as an explicit permission" below). **This specific reclassification (removing CEO from `BYPASS_ROLES`) requires human sign-off before implementation** — the evidence strongly supports it, but changing a live role's effective permissions is a business-policy action this design review does not have standing to enact unilaterally. Logged as `BC-CEO-SCOPE` (new item, not previously tracked) in the Business Confirmations section below.

## Cross-Mall as an explicit permission, not an inferred one

Per the review's Section 18 instruction: the platform has exactly one deliberately-designed cross-Mall capability today (`GET /dashboard/cross-mall`, gated to `MODULE_ROLES.crossMall = [ADMIN, CEO]`) and at least one accidentally-equivalent one (`GET /analytics/multi-mall`, reachable by the much broader `MODULE_ROLES.analytics` list including `LEASING_MANAGER`, per `docs/system-truth/15-MULTI-MALL-MULTI-COMPANY.md`). This ADR proposes a single explicit `CROSS_MALL_READ` scope/permission (a `SYSTEM/INTERNAL`-adjacent concept, technically: a route declares `@Scope(MALL, { crossMallReadRole: [...] })` rather than `MALL` meaning "exactly one resolved Mall") applied consistently to both routes, closing the inconsistency between them without inventing a new authority model. A `CROSS_MALL_OPERATE` (write) permission is **not** proposed — no current route was found requiring cross-Mall *write* capability (Dashboard's cross-mall view and Analytics' multi-mall comparison are both read-only), so this ADR does not introduce a capability with no current user.

## Reports/Analytics — technical capability vs. business policy, kept separable

Per Section 15's instruction: this ADR does not hard-code a single answer to "may users view selected Mall / assigned Malls / multiple Malls / all Malls" for Reports/Analytics. The `MALL-SCOPED` scope with the accessible-mall-set resolution (already correctly implemented in `DashboardService`, per `03-MALL-AUTHORIZATION-ARCHITECTURE.md`) technically supports all four policy variants — "assigned Malls" is the default (a user's own `UserMallAccess` set), "selected Mall" is a client-side filter narrowing that set, "multiple/all Malls" is the `CROSS_MALL_READ` permission above. The architecture doesn't need to pick one; `BC-013` (does Reports/Analytics get the same treatment as Dashboard, i.e. accessible-mall-set-by-default) is a business decision applied as a *parameter* to an already-built mechanism, not a blocker to building the mechanism itself.

## Migration strategy

Seven phases (`17-CR-101-MIGRATION-PLAN.md`), each independently revertible: (1) annotate already-correct routes, zero behavior change; (2) annotate global/exempt routes with recorded reasons, zero behavior change; (3) annotate and fix confirmed-gap routes with audit-log-first rollout per route/batch; (4) startup completeness check, warn-mode first then strict; (5) CI static gate; (6) flip to fail-closed enforcement (behind a feature flag for instant rollback); (7) remove the old heuristic code.

## Compatibility

Phases 1–5 are purely additive. Phase 3's actual fixes ship behind an observe-only audit-log window before becoming enforcing, specifically to surface any undetected legitimate cross-Mall usage empirically before it can be broken. Phase 6 is feature-flag-gated for instant rollback. No schema migration is required for the core mechanism; two confirmed-gap routes (`customers.controller.ts`, `parking-dashboard.controller.ts`) are explicitly schema-dependent and blocked on separate business/data-modeling decisions, not bundled into the core CR-101 rollout timeline.

## Performance

One additional DB lookup per request for previously-unscoped entity-based routes, designed to be reusable by the subsequent service call rather than a throwaway duplicate lookup; negligible cost for list endpoints (reuses the existing `mallIds`-array-in-`where`-clause pattern) and file-download routes. No obvious performance-collapse risk identified. See `17-CR-101-MIGRATION-PLAN.md`'s Performance section.

## Security properties

- Closes the structural root cause of `CONTRA-008`, not merely its currently-known instances.
- Converts "missing Mall-scoping" from a silent runtime gap (discoverable only by security review or incident) to a build-time/deploy-time failure (Phase 4/5).
- Establishes `INV-AUTH-001` through `INV-AUTH-005` (below) as continuously-enforced, not merely documented, invariants once Phase 6 is live.
- Narrows the ADMIN/CEO bypass surface based on actual evidenced intent rather than leaving an unexamined blanket assumption in place (pending the `BC-CEO-SCOPE` sign-off).

## Failure mode

If a resolver itself has a bug (e.g., an incorrect Prisma relation), Phase 6's fail-closed behavior means the affected route DENIES legitimate requests rather than silently over-permitting them — a false-deny is loud and immediately reported (user-visible error, presumably support-ticketed), whereas today's false-permit is invisible until discovered by audit. This is the intended tradeoff (per `INV-AUTH-003`, "unresolved Mall scope may never default to ALLOW") and is why Phase 6 ships behind a feature flag for fast reversal if a resolver defect is found in production.

## Rollback

Phases 1–5: delete added code/config, zero data impact. Phase 6: flip the feature flag back to Phase-5 (skip-if-unresolved) behavior instantly, no deploy required. Phase 7 (heuristic-code removal): only proceed after Phase 6 has soaked; reverting Phase 7 means restoring deleted code, low but nonzero friction — hence sequenced last and given its own soak-period gate.

## Consequences

- Every future new route must carry `@Scope(...)` or fail CI/startup — a small, permanent tax on adding any new controller method, in exchange for structurally eliminating this defect class.
- CEO's effective permissions narrow if `BC-CEO-SCOPE` is confirmed in the direction the evidence points — a real behavior change for real users, requiring product/support communication, not just an engineering change.
- The resolver registry becomes the single source of truth for "how do we find this entity's Mall" — future entities need a registered resolver before their routes can be properly scoped, which is a positive forcing function (per `docs/ai-governance/04-CODING-GUARDRAILS.md`'s SOURCE OF TRUTH principle) but does add a small design step to onboarding any new Mall-scoped entity.
