# 30 — CR-101 Phase 3C: File Threat Model

Audit only. Every classification below is backed by a specific, independently-re-verified code citation (see `28-...-READINESS.md` and `29-...-OWNERSHIP-MATRIX.md`), not inferred from a route's name or module.

## Threat-by-threat classification

| Threat | Classification | Evidence |
|---|---|---|
| **Cross-Mall IDOR** | **CONFIRMED** | All 8 `files.controller.ts` families: role/tenant-checked but zero Mall check. Precisely confirmed for `patrol-checks/:fileId` — the exact resolving helper (`checkMallId()`) exists, is tested, and simply isn't called. `fitout-issue.controller.ts` list/upload routes: protected only incidentally by the global guard's path-substring match, not by an explicit check. |
| **Cross-Tenant IDOR** | **PROTECTED** | Every `Role.TENANT`-reachable route re-verified this phase: `ContractFile` (`Contract.tenantId`), `UnifiedDocument` Invoice/Ticket branches, `FitoutDocument` (`FitoutProject.tenantId`), and `tickets.controller.ts`'s own photo routes (double-checked at both the controller's `MallAccessService` call and the service's `findOne()` tenant comparison). No gap found. |
| **fileId substitution** | **NOT APPLICABLE** | Every `files.controller.ts` route is keyed by the file's own primary key (`fileId` = the row's own `id`), not a client-supplied reference to a *different* record than the one being acted on. There is no "pass file A's id but read file B" vector in this controller — the vulnerability here is a *missing* check (role-only), not a substitutable-identifier one. |
| **parentId substitution** | **CONFIRMED (one instance), PROTECTED (elsewhere)** | **Confirmed**: `fitout.controller.ts`'s `PUT :id/documents/:docId/review` — the path's `id` (project) is Mall-checked, but `docId` is never verified to belong to that project; `FitoutDocumentsService.reviewDocument()` does a bare `findUnique({ id: documentId })`. **Protected elsewhere**: `contracts.service.ts` (`deleteFile`/`signFile`) and `service-contracts.service.ts` (`deleteDocument`, and `uploadDocument`'s optional `paymentId` check) all correctly scope the child lookup with a compound `findFirst({ id, parentId })` — these are the pattern the fitout fix should copy. |
| **Role-only bypass** | **CONFIRMED** | 7 of the 8 `files.controller.ts` families (`ParkingContractDocument`, `ServiceContractDocument`, `WorkOrderEvidence`, `PatrolCheck`, and the three GAP-role-only `UnifiedDocument` fitout branches) have **no owner-entity check of any kind** beyond a flat `@Roles`-equivalent class gate — any authenticated user whose role passes can fetch **any** document of that type by id, cross-Mall (the 4 with tenant checks add tenant protection but still lack the Mall dimension). |
| **Direct URL / static-mount bypass** | **PROTECTED (re-verified)** | Independently re-confirmed this phase (not inherited): `main.ts` mounts exactly 3 narrow, low-sensitivity subpaths (`floor-plans`, `branding`, `unit-media`); every private-document subfolder (`contracts`, `billing/invoices`, `fitout*`, `service-contracts`, `parking-contracts`, `patrol`, `work-orders`, `tickets`, `maintenance`) has no static mount at all — `GET /uploads/<subpath>/...` 404s regardless of any NestJS guard. No other `express.static`/`ServeStaticModule`/`sendFile`/`res.download` call exists anywhere in the backend. `StorageService.getFileStream()` is called from exactly one place (`files.controller.ts`'s `stream()` helper). The 2026-08-19 P1 remediation holds today with no regression. |
| **List leakage** | **PROTECTED, with a minor smell noted** | `tickets.service.ts`'s `listPhotos()` returns full `UnifiedDocument` rows including the raw `filePath` string in the JSON response. This is not currently exploitable — that path (`uploads/tickets/...`) isn't statically mounted, so fetching it directly still 404s — but exposing an internal storage path in an API response is unnecessary and worth tightening opportunistically (select only the fields the UI needs), not because it's a live bypass today. |
| **Preview leakage** | **NOT APPLICABLE** | No distinct "preview" endpoint exists separate from the authenticated download routes; the frontend's `AuthenticatedImage`/`openAuthenticatedFile` helpers (added in the 2026-08-19 remediation) fetch thumbnails through the same authenticated, authorized `files.controller.ts` routes as full downloads — no separate, weaker preview path found. |
| **Delete escalation** | **PROTECTED (where delete exists); NOT APPLICABLE (where it doesn't)** | Only two families have a delete route today: Contract files (`DELETE :id/files/:fileId`, correctly scoped `findFirst({id, contractId})`, EDIT-tier roles) and Service Contract documents (`DELETE :id/documents/:documentId`, same pattern). No other family (`FitoutDocument`, `ParkingContractDocument`, `WorkOrderEvidence`, `PatrolCheck`, `UnifiedDocument`-backed families) has a delete route at all currently — nothing to classify as a gap for those. |
| **Upload-to-foreign-owner** | **PROTECTED** | Every module-native upload route verified this phase validates the target parent entity's Mall access before accepting the file (`validateContract`, `assertItemAccess`, `assert()`, `checkMallId()`, `validateProject`, `validateSubmittalAccess`, the double-checked ticket-photo path) — with the one exception being `fitout-issue.controller.ts`'s incidental-only protection (works today, not independently verified at the route level). |
| **Path traversal** | **PROTECTED** | `StorageService`'s path-resolution guard (`resolveWithinUploadDir()`) rejects any resolved path escaping the upload root — confirmed not just by reading the code but by this session's own backend test runs, which log `Rejected unsafe storage path: ../outside.txt` and `Rejected unsafe storage path: C:\...\outside.txt` warnings from the live `StorageService` test suite on every run. |
| **Filename collision** | **NOT APPLICABLE to authorization** | Filenames use a `{timestamp}_{sanitizedName}` scheme (predictable, previously documented). A collision could theoretically cause one upload to overwrite another *within the same caller's own upload flow*, but does not grant any actor access to a file they aren't already authorized to write to — a data-integrity nit, not an authorization bypass. Not investigated further as out of scope for this authorization-focused review. |

## Authorization invariants (refined against actual code, not the generic template)

**INV-FILE-001** — A document may only be read when the actor is authorized for its authoritative owner (Tenant match for tenant-owned families, Mall access for staff). **Currently satisfied for the Tenant dimension across every family checked. Currently violated for the Mall dimension across all 8 `files.controller.ts` families** — this is the `AUTH-01` cluster, re-confirmed unchanged.

**INV-FILE-002** — Mall-scoped staff cannot access a document owned by a Mall they lack `UserMallAccess` for, unless they hold a bypass role (`ADMIN`/`CEO`, per existing platform convention) or an explicit cross-Mall permission (none exists for files today, and none is proposed here — no route was found needing cross-Mall document read). **Currently violated** for the same 8 families, and incidentally-only-satisfied for `fitout-issue.controller.ts`.

**INV-FILE-003** — Tenant users cannot access documents owned by another Tenant. **Currently satisfied**, verified across every `Role.TENANT`-reachable route.

**INV-FILE-004** — A client-supplied secondary/child identifier (e.g. `docId` alongside an already-Mall-checked `projectId`) cannot be acted upon without independently verifying it belongs to the already-authorized parent. **Currently violated in exactly one confirmed instance** (`fitout.controller.ts`'s `reviewDocument`); **satisfied everywhere else checked** (contracts, service-contracts).

**INV-FILE-005** — Delete/replace operations require explicit write-tier role authority (not merely read-tier), evaluated separately from read authorization. **Currently satisfied** for both families that have a delete route.

**INV-FILE-006** — No protected document's bytes may be reachable other than through its authenticated, per-record-authorized controller route. **Currently satisfied**, re-verified this phase with no regression from the 2026-08-19 remediation.

## Net severity assessment

- **P1** (2 confirmed, both narrow and bounded): `patrol-checks/:fileId`'s missing Mall check (one-line fix available), `fitout.controller.ts`'s `reviewDocument` parentId-substitution bug (small, well-understood fix pattern already used elsewhere in the codebase).
- **P1-class but broader** (the `AUTH-01` cluster itself): the remaining 7 `files.controller.ts` families' missing Mall check — same severity class as `patrol-checks`, larger in count but each individually small/bounded (§29's `READY_WITH_EXISTING_QUERY`/`REQUIRES_NEW_RESOLVER` classifications).
- **P2**: `fitout-issue.controller.ts`'s incidental-only protection; `ai.controller.ts`'s 3 unguarded analysis routes (out of scope, AI is Phase 3D); the ticket-photo list-leakage smell.
- **No P0 found** in this review — no unauthenticated access, no cross-Tenant IDOR, no direct storage bypass.
