## Method
- `Role.CEO`'s route-level access is controlled by `@Roles(...)`, almost always backed by `MODULE_ROLES` in `apps/backend/src/common/constants/role-permissions.ts`; a few controllers (`service-contracts`, `work-orders`) define their own local role-array constants instead of using `MODULE_ROLES`.
- Separately, `MallAccessService.BYPASS_ROLES = [ADMIN, CEO, TENANT]` means CEO skips **all Mall-scoping** wherever it has route access at all. Bypass does **not** grant route access by itself — a route's own `@Roles`/role check runs first and independently (confirmed by direct code read of `files.controller.ts`, where several sibling routes use near-identical Mall-bypass-eligible patterns but differ in whether CEO is in the role list at all).
- Persona baseline quoted verbatim from `docs/audit/02-PERSONAS-JOBS-TO-BE-DONE.md:107-110`: *"CEO gets cross-mall, analytics, approvals (final-tier), reports, ai — deliberately excludes day-to-day operational detail (no spaces/crm/bookings/tickets)."*

## Headline corrections to the earlier `25-CR-101-BUSINESS-DECISION-PACK.md` draft

1. **Work Orders was missing entirely from the earlier matrix.** It is now the single largest confirmed contradiction found in this pass — CEO has full operational CRUD (create/update/status-transition/review/template-authoring/CSV-export), a clean textbook violation of "deliberately excludes day-to-day operational detail."
2. **Service Contracts was missing entirely.** Turns out to be a *clean* case (read+export only, no write) — no contradiction, unlike Parking/Proposals/Work Orders.
3. **Sales was missing entirely.** Partial contradiction: `approve`/`dispute` fit an oversight framing, but sales-record *creation* does not.
4. **Files/document-access was not previously cross-referenced against module access at all.** Doing so surfaces a structural inconsistency independent of the CEO question: `files.controller.ts`'s Ticket branch has no role gate (any staff role, not just CEO, can download ticket documents) while `tickets.controller.ts` itself has no CEO access whatsoever — an odd asymmetry, noted here as a File-domain observation, not something this review is authorized to fix (File authorization architecture is CLOSED per this authorization's Section 13).
5. **Fitout-Submittal's approval steps are policy-data-driven and could theoretically name CEO as an approver** for a non-Proposal entity type, though nothing in current seed/config data does so today. Flagged as a minor design note.

## Correction — CR-101 Phase 3G implementation (2026-08-22)

**This is an explicit correction, not a silent edit — the matrix rows above are left as originally written.**

During implementation of the approved BC-CEO-SCOPE Option A decision, re-reading `proposals.controller.ts` and `parking.controller.ts` directly (rather than relying on this matrix's own prior text, which had itself carried forward a claim from the earlier `25-CR-101-BUSINESS-DECISION-PACK.md` draft without re-verifying it against current code) found that **both the Proposals and Parking rows above are wrong**:

- **Proposals**: every mutating route (`create`, `update`, `submit`, `convert`, `remove`, `reject`, `editor-content`, `doc-fields`, scenario create/update/delete/select) already carries its own method-level `@Roles(...)` override (`PROPOSAL_EDIT_ROLES`, `PROPOSAL_CONVERT_ROLES`, or an explicit list) that **excludes CEO** — confirmed by grepping the file for `Role.CEO`: zero matches. CEO's actual Proposals access today is read-only (list/detail/stats/pdf-export/versions) plus its Approvals-driven final-tier action — **already fully consistent with the documented persona**, not a contradiction.
- **Parking**: `parking.controller.ts`'s `EDIT`/`FINANCE_EDIT` role constants (used on every contract/rate/payment/statement mutation route) **already exclude CEO** — `EDIT = [ADMIN, MALL_DIRECTOR, OPERATION, FINANCE, LEASING_MANAGER]`. CEO's actual Parking access is `VIEW`-only (dashboard/alerts/contracts list+detail/statements, plus the two CSV exports, which have no override) — **already fully consistent with the documented persona**.

**No code change was made to either controller this phase** — there was nothing to fix. The two real, code-verified contradictions requiring a fix were **Work Orders** (full operational CRUD, the largest confirmed contradiction of the whole review) and **Sales** (record-creation), plus **Analytics** (Mall-policy/retention config-write) — all three closed in `docs/changes/CR-101-PHASE-3G-IMPLEMENTATION-COMPLETION.md`.

This correction is disclosed prominently because the human decision that authorized this implementation explicitly named Proposals and Parking as domains to narrow, based on this matrix's original (incorrect) text — per this program's standing rule to verify every claim against executable code rather than trust prior audit text, this was caught and corrected before implementing a change that would have had no effect (both controllers were already correct).

## Cross-cutting fact confirmed once, applies to every "YES" cell above
Every domain where CEO has *any* role-level access is **completely unscoped by Mall** (`BYPASS_ROLES` membership) — a CEO with read/write on Parking, Work Orders, Proposals, or Sales today can act on **any Mall on the platform**, not a documented or assigned subset. This is the concrete mechanism behind every "Unrestricted" cell above.
