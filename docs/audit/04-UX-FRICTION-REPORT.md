# 04 — UX Friction Report

> Phase 4. Every finding below is grounded in a concrete file/behavior found in
> the codebase (see research summaries folded into 00–03), not a general ERP
> assumption. Severity: Critical / High / Medium / Low.

| ID | Screen/Area | Persona | Problem | Impact | Severity | Recommendation |
|---|---|---|---|---|---|---|
| FR-01 | Sidebar → Fitout (tenant) | Tenant | Frontend `ROUTE_PERMISSIONS.fitout` grants TENANT access to `/fitout`; backend `MODULE_ROLES.fitout` does not include `Role.TENANT`. Tenant clicking this nav item hits a 403/empty result. | A real, reachable dead link for external users — the worst kind of friction, since tenants have no one to ask. | **Critical** | Remove `/fitout` from `TENANT_NAV`/`ROUTE_PERMISSIONS` (tenants already get fitout status inside Tenant Portal) or explicitly grant backend access if intended. One-line fix each side. |
| FR-02 | Proposals (navigation) | Leasing Executive/Manager, new users | There is no "Create Proposal" entry point under the Proposals module at all — proposal creation only exists inside Bookings (`ConvertToProposalDialog`). A new user opening `/proposals` looking to start one will not find a way to. | New-user "I don't know where to start" — directly matches the platform-wide stated problem. | **Critical** | Add a visible "Tạo đề xuất" primary action on the Proposals list that either deep-links to Bookings-with-unit-picker or opens the same conversion dialog pre-filtered to "select a booking." Don't require the user to already know the data model. |
| FR-03 | Sidebar → Parking | Operation, Finance | Parking is split across two nav groups: `operations` ("Vận hành bãi xe" → `/parking`) and `parkingCentral` ("Báo cáo bãi đỗ xe" / "Giao dịch bãi đỗ xe"). One subject, two unrelated-looking menu locations. | Recognition-over-recall failure — user has to remember which group parking reporting lives in. | High | Merge into a single "Bãi đỗ xe" group with 3 items (Vận hành, Giao dịch, Báo cáo), or nest report/transaction as sub-tabs of the main Parking page. |
| FR-04 | Approvals queue | Manager/Director/CEO/Finance/Legal | The pending-approvals list shows step/status only — discount %, rent-free days, and *why this step exists* (which policy rule fired) are not shown inline; approver must open the Proposal separately to get decision context. | Adds a screen switch to every single approval decision — the platform's highest-frequency executive action. | High | Show a compact deal-context summary (unit, tenant, discount %, rent-free days, which threshold triggered this step) directly in the approval row/card. See 07-DASHBOARD-REDESIGN. |
| FR-05 | Approval policy computation | Leasing Exec/Manager (submitter) | The multi-step approval chain is built silently server-side from `ApprovalPolicyRule` (discount/rent-free/AR-debt/price-deviation thresholds). The submitter sees the resulting pipeline only after submitting — never a preview of "this will need Mall Director + CEO because discount is 12%." | Submitter can't anticipate approval time/effort before committing; also makes the rule engine feel opaque ("why does this need 3 approvals and that one only needs 1"). | Medium | Show a live "this proposal will require: Leasing Manager → Mall Director → CEO (discount >10%)" preview on the proposal edit screen before submit, computed client-side from the same thresholds or a dry-run endpoint. |
| FR-06 | Proposal→Contract conversion | Leasing Manager | A single button click creates a Contract + (conditionally) a Tenant + updates Unit status — a real multi-entity fan-out — with no preview/confirmation step showing what's about to be created. | High-consequence action with a plain-button affordance; violates ERP_UX_STANDARD's "what will happen if I press this button" principle for exactly the highest-stakes action in the platform. | High | Add a one-screen "Review before creating contract" confirmation (tenant to be created, unit to be marked ACTIVE, contract terms summary) before the mutation fires. |
| FR-07 | Notification Center | All staff | All notification types (SLA breach, escalation, AI insight, "proposal approved" informational update, reminders) render in one flat, undifferentiated feed with only read/unread state — no type icon, no severity, no filter. Backend already carries distinct `type` values that could support this. | User cannot tell "this needs me to act" from "this is FYI" without opening every item — directly the "not knowing what's waiting on me" problem named in the audit brief. | **Critical** | Split into Notifications (informational) vs. Tasks (action-required) per Phase 10 standard; see 09-TASK-NOTIFICATION-CENTER for full spec. |
| FR-08 | Dashboard "Executive Actions" | All staff | The action list is a fixed set of 6 item types (overdue invoices, expiring contracts ×2, open tickets, expiring bookings, pending approvals). It does not include fitout SLA breaches, patrol shift issues, or work-order due-soon items — even though those already generate notifications elsewhere in the system. | Operation-focused roles (whose `focusAreas` are `['tickets','fitout']`) get an incomplete "what needs me" view — fitout escalations exist but never surface on their dashboard action list. | Medium | Extend `ActionItems` to include fitout SLA breaches and (for Operation) work-order/patrol overdue counts, filtered the same way existing items are by `focusAreas`. |
| FR-09 | Empty states — Contracts, Proposals, Billing Invoices | All staff, new users | Three of the four highest-traffic list screens show only an icon + one line of text ("Không có hợp đồng nào") with **no CTA and no distinction** between "genuinely empty" and "no results for your filter." Tickets, in the same codebase, has the correct pattern (contextual CTA: clear filters vs. create). | New users hitting an empty list get no guidance on what to do next — directly the stated "self-service" and "system should guide me" goals. | High | Bring Contracts/Proposals/Billing Invoices up to the Tickets pattern (already exists as `AsyncState`/`EmptyState` shared component, just underused) — this is a "use what exists" fix, not new design. |
| FR-10 | Operation role | Operation staff | One `OPERATION` role covers Service Contracts, Inventory, Work Orders, Patrol, Parking, Fitout, Tickets — 7 functionally unrelated areas, all shown with equal nav prominence to every Operation user regardless of their actual job (dispatcher vs. patrol guard vs. fitout coordinator). | Cognitive overload for the role with the least technical training, per persona research (Persona E). | High | Not a quick fix — requires either sub-role/permission scoping or a personal "pin/hide modules I don't use" nav preference. Flagged as P1/strategic in the priority matrix, not P0. |
| FR-11 | Reporting surfaces | Director, CEO, Finance | 6 separate surfaces (Dashboard, Reports, Analytics, Cross-Mall Dashboard, Pipeline Stats, Deal Pipeline) compute overlapping occupancy/pipeline/revenue KPIs with no stated distinction of purpose. Independently flagged in V2. | User can't tell which one is authoritative or which to open for a given question — recognition-over-recall failure at the IA level. | High (carried from V2, restated here as a UX/IA problem) | Consolidate per V2 Sprint D + this audit's IA proposal: Operational Dashboard vs. Commercial Performance vs. Finance/Compliance Reports, each with a one-line stated purpose. |
| FR-12 | Sidebar grouping | All staff | `operations`, `finance`, `analytics`, `system` groups are organized by backend module/domain, not by task sequence — inconsistent with the `salesProcess`/`crm` groups, which the code comments confirm *were* deliberately designed around task sequence. The `ErpProcessGuide` strip exists specifically to compensate for this inconsistency. | Half the platform teaches "what to do next," the other half requires already knowing the org chart / module names. | High | Apply the same task-sequence lens used for `salesProcess` to `operations` (e.g., "Xử lý sự cố" grouping Tickets+WorkOrders, "Thi công" grouping Fitout) — see 06-INFORMATION-ARCHITECTURE. |
| FR-13 | Two hand-synced permission tables | Admin/Engineering, indirectly all users | `role-permissions.ts` (backend) and `permissions.ts` (frontend) are independently maintained with a comment noting they must stay in sync — FR-01 is a live instance of this drifting. | Latent risk of more silent dead-links/mismatched 403s as roles evolve. | Medium | Generate one from the other (or a shared JSON) at build time — engineering fix, but the user-facing symptom (dead links) is a UX defect. |
| FR-14 | High-tab-count screens (Fitout, Billing, Contracts, CRM) | All staff | Fitout ~15 tabs, Billing 11 (incl. sub-tabs), Contracts 7, CRM is a 2,500-line monolith. Independently confirmed in V2's complexity table. | Information friction — data relevant to one decision is spread across many tabs with no summary-first view. | High (carried from V2) | See per-screen redesign specs in `docs/redesign/`; apply progressive disclosure (summary tab first, detail tabs behind it) rather than flat tab bars. |

## Friction by category (rollup)

- **Navigation friction:** FR-03, FR-12 — inconsistent grouping logic, one subject
  split across groups.
- **Cognitive friction:** FR-05, FR-10 — invisible policy logic, one role covering
  unrelated jobs.
- **Interaction friction:** FR-06 — high-consequence single-click actions with no
  preview.
- **Workflow friction:** FR-02, FR-04 — missing entry points, decision context not
  co-located with the decision.
- **Information friction:** FR-04, FR-11, FR-14 — data spread across screens/tabs,
  no stated purpose per reporting surface.
- **Visual/state friction:** FR-07, FR-08, FR-09 — undifferentiated feeds, missing
  empty-state CTAs.
- **RBAC/access friction:** FR-01, FR-13 — drifted permission tables producing dead
  links.

Critical items (FR-01, FR-02, FR-07) are candidates for **P0 — must fix before
Go-Live**; see [12-GO-LIVE-READINESS](12-GO-LIVE-READINESS.md) and the priority
matrix in [14-IMPROVEMENT-ROADMAP](14-IMPROVEMENT-ROADMAP.md).
