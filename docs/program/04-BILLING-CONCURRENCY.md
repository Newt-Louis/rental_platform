# 04 — Billing & Finance: Concurrency Matrix

**Date:** 2026-08-19. Scenarios adapted from the phase brief's list to what
actually exists in this schema — there is no separate Payment-Allocation
entity (see `04-BILLING-DOMAIN-MAP.md`), so "two allocation requests" is
replaced with the real equivalent risk in this domain.

| # | Scenario | Mechanism that resolves it | Expected result | Verified this phase |
|---|---|---|---|---|
| 1 | Two invoice-generation workers process the same billing period concurrently | `Serializable` transaction per invoice in `generateDueInvoices`; deterministic `invoiceNumber = INV-SCHEDULE-<scheduleRowId>` makes a collision hit the DB's unique constraint (`P2002`), caught and repaired (links the existing invoice, doesn't error or duplicate) | Exactly one invoice per schedule row, regardless of how many workers race | Yes — code-verified (Phase 2), re-verified unchanged this phase |
| 2 | Two manual "Issue" requests on the same invoice (double-click / retry) | `Serializable` transaction, in-transaction re-read of `Invoice.status`; a second call sees `ISSUED` (not `DRAFT`) and takes the idempotent-replay branch instead of re-issuing | Exactly one issuance; the loser's request still succeeds (returns the already-issued invoice), doesn't error | **Yes — new this phase.** `issueInvoice()` hardened + tested (`billing.invoice-issue.spec.ts`) |
| 3 | Duplicate payment callback (same `idempotencyKey` submitted twice, e.g. a webhook retry) | `idempotencyKey` + payload-hash pre-check, `Serializable` transaction, `P2002` DB-constraint fallback if both requests race past the pre-check | Exactly one `Payment` row; both callers receive the same result | Yes — code-verified (Phase 2 gold-standard finding), unchanged this phase |
| 4 | Same invoice: a payment posts while a separate request records an adjustment (credit note) concurrently | Both `recordPayment` and the adjustment-creation path (`billing.adjustment.spec.ts`) run their own `Serializable` (or equivalent, per that spec) transaction, and `recomputeInvoiceStatusFromPayments` always recomputes `status`/`balance` from the *current* full set of active payments + `adjustmentAmount` rather than incrementing a cached running total | Whichever commits second sees the other's effect already reflected — no lost update, because neither path trusts a stale in-memory balance | Re-verified this phase (read, not re-tested — existing `billing.adjustment.spec.ts` coverage judged sufficient, no code change made to this path) |
| 5 | Dunning job selects an overdue invoice for a reminder at the same moment a payment clears it | **Not resolved by locking — inherent eventual-consistency window, documented rather than engineered away.** `ArDunningService.runDunningUnlocked` reads `invoice.status IN (ISSUED, PARTIALLY_PAID, OVERDUE)` and independently computes `outstanding` in the same query pass; if a payment commits *after* that read but *before* the reminder email is actually sent, the tenant could receive one reminder for a debt that was just paid. This is the same class of gap the SLA-breach email path already has (Phase 2 finding) — a single-pass batch read, not a live check right before send. **Not fixed this phase**: the reminder is only sent once per policy level (`ArDunningLog @@unique([invoiceId, policyId])`), so the worst case is one slightly-stale reminder, not a repeating one — low severity, and adding a re-check-before-send would need its own transaction design better suited to a dedicated Dunning-reliability pass, not squeezed into this phase's activation/issuance scope. | One possible stale reminder per overdue invoice, never repeating | Documented, not fixed — recorded as new backlog (see `RELIABILITY_BACKLOG.md` item 11) |
| 6 | Contract termination (`ContractTerminationService.initiate`) races with billing-schedule generation for the same contract | `ContractsService.updateStatus` (the only path that calls `buildScheduleForContract` for an *activating* contract) and `ContractTerminationService.initiate` (which requires `status IN (ACTIVE, EXPIRING)` and moves to `TERMINATING`) can't both be mid-flight against a meaningfully overlapping state — activation only ever starts from `DRAFT`/`PENDING_LEGAL`/`PENDING_SIGNATURE`/`EXPIRING`, never from `TERMINATING`. The scenario that *was* a real gap — the **manual** rebuild endpoint (`POST /billing/schedule/:contractId/build`) being callable on a `TERMINATING`/`TERMINATED` contract with no status guard — is fixed this phase (see `04-BILLING-FINANCE-COMPLETION.md`). | A terminated (or terminating) contract's billing schedule can never be (re)built via any path, manual or automatic | **Yes — new this phase.** `billing-schedule.service.spec.ts` covers the guard directly |
| 7 | Two users try to activate the same contract concurrently (billing-schedule side-effect of Contract Activation, not new to Phase 4) | Covered in Phase 3 (`P2034` serialization-conflict resolution) — billing-schedule generation is now inside that same transaction, so this scenario's billing-side outcome inherits Phase 3's guarantee: one winner, one schedule, no partial state | One contract activation, one schedule generation, no duplicate/missing schedule | Yes — Phase 3, re-confirmed still true this phase (schedule generation join was verified in the Phase 3 test suite, unchanged) |

## Scenario explicitly out of scope (no entity exists for it)

"Two allocation requests race for the same payment" — not applicable.
`Payment.invoiceId` is a fixed FK set at creation; there is no separate
allocation step that could race independently of payment creation itself
(covered by scenario 3).
