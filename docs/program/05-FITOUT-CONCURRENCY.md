# 05 — Fitout & Handover: Concurrency Matrix

**Date:** 2026-08-19.

| # | Scenario | Mechanism that resolves it | Expected result | Verified this phase |
|---|---|---|---|---|
| 1 | Duplicate Fitout auto-create (concurrent/redelivered `contract.activated` events for the same contract) | `FitoutProject.contractId @unique` + Serializable transaction + `P2002` repair | Exactly one `FitoutProject` per contract, regardless of delivery count | **Yes — new this phase.** `fitout-lifecycle.spec.ts` |
| 2 | Two stage advances on the same project (different targets, e.g. one user clicks "Inspection", another clicks "Approved to Open" moments apart) | In-transaction re-read: if the project already moved to a *different* status than the one the request was validated against, reject with a clear conflict error | One winner (whichever transaction commits first); the loser gets a clear "status changed, refresh and retry" error, no silent overwrite, no double transition | **Yes — new this phase.** `fitout-lifecycle.spec.ts` |
| 3 | Two identical stage-advance requests (double-click, same target) | In-transaction re-read: if the project already reached the *exact* target status, treat as an idempotent no-op | Both callers see success with the same resulting status; no duplicate `FitoutMilestone`/`AuditLog` rows | **Yes — new this phase.** `fitout-lifecycle.spec.ts` |
| 4 | Submission vs. stage advance (a submittal is approved — moving `FitoutSubmittal.status` — at the same moment an operator manually advances the project stage) | Independent transactions on independent primary state (`FitoutSubmittal.status` vs `FitoutProject.status`); the stage-advance transaction's gate check reads `FitoutSubmittal.status` fresh at the start of its own transaction, so it sees whichever committed first — no shared-write conflict between the two flows | Deterministic based on commit order; no corruption in either table | Not independently test-covered this phase — reasoned from the code (no shared row is written by both flows) rather than a dedicated concurrency test, given time budget; flagged, not fabricated as tested |
| 5 | Approval vs. resubmission (an approver approves a submittal at the same moment the submitter resubmits a rejected one) | Not traced this phase — `resubmit()`'s internals weren't read in depth (see `05-FITOUT-STATE-MACHINE.md`, no reliability question was raised against this specific path in Phase 2's findings) | Not analyzed | **Not verified — explicitly out of scope this phase, not claimed safe** |
| 6 | SLA job vs. stage completion (`FitoutSlaService.checkSlaBreaches` cron marks a milestone overdue at the same moment `advanceStatus` completes it) | Same eventual-consistency class as the Billing dunning-vs-payment scenario (`04-BILLING-CONCURRENCY.md` #5) — the cron reads milestones in a batch pass; a completion landing between that read and the escalation email being sent could produce one stale escalation notice. Not engineered away — same reasoning as the Billing case: low severity, doesn't repeat, would need its own dedicated redesign to close fully. | At most one stale SLA-breach notification per milestone, never repeating | Documented, not fixed — consistent with how the equivalent Billing scenario was handled |
| 7 | Handover vs. late stage update (someone tries to advance past `OPENED`, or advance a different stage after the project already reached the terminal stage, while another update is in flight) | `OPENED` has no further stages after it (`newIdx` will never resolve past the last configured stage) combined with the same forward-only + in-transaction re-check as scenario 2/3 | Any attempt to advance a project already at the terminal stage either fails validation (unknown/not-later stage) or hits the same idempotent/conflict resolution as scenario 2/3 | Covered by the same `advanceStatus` hardening and its general test coverage — not a separately distinct code path, so not given a separate dedicated test |
